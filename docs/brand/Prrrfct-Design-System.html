01 — About this system

Foundations + tokens + components.

The Prrrfct Design System is the working layer between brand expression and product UI. It keeps every screen calm, consistent, and accessible — without inventing styles on the fly.

Code is the source of truth. Tokens live in globals.css and tailwind.config.ts. Components live in components/ui/**. Documentation follows those files — never ACME demo data.

Operating principle · PROJECT_CONTEXT.md
Foundations

Primitives that do not drift

Color, type, spacing, radius, and breakpoints. Defined once as CSS custom properties, consumed through semantic aliases and Tailwind theme keys.

Design tokens

Decisions as variables

Self-contained design decisions — a color, a size, a type scale — mapped from primitive → semantic → utility class so product code stays intentional.

Components

Interactive building blocks

Button, Text, Input, Card, Logo, links, care and social cards — adapted shadcn/ui patterns locked to Prrrfct tokens and WCAG 2.2 AA.

Brand Book

Expression, not implementation

The Brand Book covers personality, logo, imagery, and voice. This Design System covers how those values become measurable UI tokens and components.

Structure note. Documentation IA (About → Foundations → Design tokens → Components → Rules) was inspired by the Specify/Notion Design System template. All actual values in this document come from the live Prrrfct repo — coral brand, Plus Jakarta Sans, and mono scale — not the ACME violet/Inter demo content in that template.

02 — Foundations

The shared visual grammar.

Foundations are the non-negotiable building materials. Product features compose with them; they do not redefine them.

Color

Brand · Mono · Feedback

Three brand corals, a 16-step mono scale, and four feedback hues. Semantics map fills, text, and strokes onto those primitives.

Typography

Plus Jakarta Sans

One family. Ten roles from H1–caption. Mobile-first sizes step up at the lg (1280px) breakpoint.

Spacing

4 → 64px scale

Named steps 2xs through 5xl, plus layout aliases for page padding, container padding, and section margin.

Shape & layout

Radius · breakpoints · widths

Interactive and container radii, full-pill buttons, screens at 768 / 1280 / 1440, and responsive max-widths for page and form.

08 — Usage rules

Do & don’t — from PROJECT_CONTEXT.

These rules are non-negotiable. If an instruction conflicts with them, the rule wins.

Do

  • Use only Prrrfct tokensClasses from tailwind.config.ts: p-md, text-primary, bg-brand-primary.
  • Semantic HTMLReal buttons, links, inputs, and heading hierarchy — no div soup.
  • WCAG 2.2 AAKeyboard access, logical focus order, focus rings, labeled fields.
  • Ask before foundation changesglobals.css, tailwind.config.ts, and components/ui are locked.
  • Check existing tokens firstReuse before inventing.

Don’t

  • Default Tailwind utilitiesForbidden: p-4, mt-2, text-gray-500, stock color/spacing scales.
  • Invent tokens casuallyNo one-off CSS vars or arbitrary palette expansions.
  • Restyle components/uiDon’t fork Button/Input styles in feature code.
  • Skip accessibilityNo unlabeled icons, trapped focus without escape, or mouse-only affordances.
  • Copy ACME / Specify demo valuesViolet #624de3, Inter, and template measurements are not Prrrfct.

Accessibility baseline

Keyboard

Mandatory

All interactive elements reachable and operable. Focus order matches visual order.

Modals

Trap · lock · restore

Focus trap, background scroll lock, restore focus on close.

Icons

Decorative vs labeled

Decorative icons: aria-hidden. Meaningful controls need accessible names.

Live regions

aria-live sparingly

Only when necessary for status updates users can’t otherwise perceive.

09 — Implementation notes

Where to edit — and what stays locked.

Shared foundation must remain consistent across branches. Change it deliberately, then merge intentionally.

Locked

Read-only by default

  • globals.css
  • tailwind.config.ts
  • components/ui/**
  • lib/**
  • postcss.config.mjs
  • tsconfig.json · next.config.mjs
  • package.json + lockfile
  • PROJECT_CONTEXT.md · .cursorrules
Controlled

Change with care

  • app/layout.tsx
  • components/layout/*
  • EmailSignupForm.tsx
  • Providers / auth wiring
Flexible

Branch-specific OK

  • Marketing sections
  • app/page.tsx content
  • Feature routes (care, store, onboarding)
  • Copy & visual content

Stack (fixed)

Next.js 14 App Router · TypeScript · Tailwind (custom tokens only) shadcn/ui adapted to Prrrfct · Framer Motion (minimal) · Firebase · Netlify

How to extend safely

1. Read PROJECT_CONTEXT.md and classify the target file 2. Inspect existing patterns in components/ui before writing new UI 3. Prefer semantic tokens over new primitives 4. If a foundation change is required — ask, then update docs
Changelog practice. When tokens or locked components change, note foundations impacted (color, type, spacing, component name) in the PR. This Design System document should be regenerated from code after intentional foundation merges.
